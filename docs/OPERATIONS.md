# 運営ガイド & 改善提案

VOCABUKI EVENT CALENDAR の構成・運用手順と、現状の点検で見つかった課題への提案をまとめたものです。

---

## 1. 今の構成

```
                 ┌──────────────┐
   Claude ──MCP──▶│              │
                 │ events.json  │──fetch──▶ index.html （公開カレンダー）
 admin.html ─────▶│  （唯一の    │
   （ブラウザ）    │   データ源）  │
                 └──────────────┘
                        ▲
                        └── GitHub Contents API 経由でコミット
                            → GitHub Pages が 1〜2 分で再ビルド
```

- **公開ページ**: `index.html`（カレンダー本体。About / Q&A / イベント診断も内包）
- **管理ページ**: `admin.html`（パスワード + GitHub PAT でログインして編集）
- **MCP サーバー**: `mcp/server.mjs`（Claude から直接編集。→ [mcp/README.md](../mcp/README.md)）
- **データ**: `events.json` ただ 1 ファイル

`events.json` のトップレベル構造:

| キー | 内容 |
| --- | --- |
| `events` | イベント配列（スキーマは [mcp/README.md](../mcp/README.md#イベントのフィールド)） |
| `tags` | タグマスタ `{id, label, color}` |
| `people` | 出演者マスタ `{X の ID: {name, x}}` |
| `dayBgMap` | 日付ごとのカレンダー色の上書き |
| `closedDays` | 休業日（カレンダーに「休」と表示） |
| `watchAccounts` | スクレイパーの監視対象アカウント |

## 2. 日常の運用手順

### イベントを追加する

**Claude から（推奨）**
: 「9/5 に◯◯を追加して、DJ は〜」と伝えるだけ。詳細・画像・リンクまで一度に入ります。→ [mcp/README.md](../mcp/README.md)

**admin.html から**
: 週を選んで「＋ イベントを追加」→ カードを開いて編集 → カード内の「💾 保存」→ **画面上部の「💾 保存」**（これを押さないと GitHub に反映されません）

どちらで編集しても同じ `events.json` を触るので、混ぜて使って問題ありません。

### 反映の確認

保存から 1〜2 分で `https://vocabuki-io.github.io/eventcalendar/` に反映されます。
反映されないときは、GitHub の Actions タブで Pages のビルドが失敗していないか確認してください。

### 出演者の名前

`people` に一度登録すれば、以降は X の ID を書くだけで表示名とアイコンが出ます。
アイコンは `unavatar.io` 経由で X から自動取得しているので、こちらで用意する必要はありません。

## 3. 今回直した不具合

| 箇所 | 症状 | 原因 |
| --- | --- | --- |
| `index.html` 全体 | **曜日が 1 日ずれて表示されていた**（金曜のイベントが「土」など） | 曜日配列が月曜始まりなのに `Date.getDay()`（日曜始まり）で引いていた。6 箇所 |
| `index.html` リスト表示 | 月の並び順が `1月 → 10月 → 11月 → 12月 → 2月` になっていた | 月キーがゼロ埋めされておらず文字列ソートが崩れていた |
| `index.html` UP NEXT / リスト | 追加した順によっては日付順に並ばなかった | 表示前に日付でソートしていなかった |
| `admin.html` 保存処理 | イベントを保存するたびに、本来 `dayBgMap` に入るはずの `dayBg` が**イベント本体に紛れ込んでいた** | 編集用の下書きをそのままイベントにマージしていた |
| `admin.html` 保存処理 | イベントの日付を変更すると、**古い日付のカレンダー色が消えずに残っていた** | 変更前の日付を `dayBgMap` から消していなかった |
| `admin.html` ログイン | PAT を `github_pat_` 込みで貼ると認証に失敗した | トークンに常に `github_pat_` を足していた。今はどちらの形式でも通る |
| `admin.html` 保存処理 | 保存のたびにイベントの並び順が崩れていた | 保存時に日付でソートするようにした |
| 両ファイル | 出演者リストのないイベントを開くと画面が真っ白になった | `djs` / `vjs` が無い場合を考慮していなかった |
| `index.html` UP NEXT | 翌月に予定があるのに「今月はもうイベントがありません」と出た | 実際は「今日以降」を見ているので、月に限定しない文言に変更 |

## 4. 改善提案

### 4-1. 使わなくなったファイルを整理する（優先度: 中）

点検した範囲では、次の 4 ファイルは**どこからも読まれていません**。`events.json` に同じ内容が入っており、二重管理になっています。

| ファイル | 状況 |
| --- | --- |
| `events-2026-Q1.json` | `events.json` の 1〜3 月分と重複。誰も読んでいない |
| `events-2026-Q2.json` | `events.json` の 4〜6 月分と重複。誰も読んでいない |
| `people.json` | `events.json` の `people` と重複。誰も読んでいない |
| `meta.json` | `events.json` の `tags` などと重複。誰も読んでいない |

**提案**: これらを削除して、データ源を `events.json` 一本に統一する。
古い方を見て「更新したのに反映されない」と悩む事故を防げます。消しても Git 履歴に残るので、いつでも戻せます。

> 実際に消すかどうかは運営判断なので、今回は残したままにしてあります。消してよければ言ってください。

### 4-2. スクレイパーの扱いを決める（優先度: 中）

`.github/workflows/scrape.yml` が 5 時間おきに X をスクレイピングして `posts.json` に書き込んでいますが、

- **`posts.json` を読んでいるコードが存在しません**（取得したデータが行き止まり）
- X のログインを ID / パスワードで自動化しており、X 側の仕様変更や認証強化で高確率で止まります
- 失敗しても誰も気づかない状態です

**提案（どれか一つ）**:

1. **止める**: ワークフローを `workflow_dispatch` のみにして定期実行を外す。今は Claude 経由で直接登録できるので、自動取得の必要性が下がっています
2. **繋ぐ**: `posts.json` の内容を admin.html に「取り込み候補」として表示し、人が確認して `events.json` に登録する導線を作る
3. **置き換える**: 告知ポストの URL を Claude に渡して読み取らせ、そのまま `create_event` させる（追加の実装なしで今日からできます）

いま一番手軽なのは **3** です。運用が固まるまで **1** で止めておくのも手です。

### 4-3. フライヤー画像の入れ方を統一する（優先度: 高）

`admin.html` の画像アップロードは、画像を **base64 のまま `events.json` に埋め込みます**。

- `events.json` は**訪問者全員が毎回ダウンロードするファイル**です。1MB のフライヤーを 1 枚入れると、全員の通信量が約 1.3MB 増えます
- 数枚入れただけで初回表示が目に見えて重くなり、さらに GitHub Contents API の 1MB 制限を超えると `admin.html` からデータを読めなくなります

**提案**: 画像は `images/` に**ファイルとして**置き、`events.json` にはパスだけ入れる。
MCP の `upload_image` はすでにこの方式で、`images/xxxx.jpg` という短いパスを返します。

```
Claude:「このフライヤーを 9/5 のイベントに設定して」
  → upload_image  … images/20260905-flyer.jpg として保存
  → update_event  … flyer に "images/20260905-flyer.jpg" を設定
```

`admin.html` の直接アップロードは、当面「軽い画像だけ」に留めるのが安全です。

### 4-4. 管理ページの鍵はトークンだと理解しておく（優先度: 高・運用のみ）

`admin.html` はブラウザだけで動く静的ページなので、パスワードの照合も JavaScript の中で行われています。ページのソースは誰でも読めるため、**パスワードは「うっかり防止」以上のものにはなりません**。

実際に編集をブロックしているのは **GitHub の PAT** です。したがって:

- PAT は**編集する人ごとに個別に発行**する（誰の操作か履歴で追え、辞めた人の分だけ失効できる）
- 権限は `vocabuki-io/eventcalendar` の **Contents: Read and write だけ**に絞る
- 有効期限は 90 日など短めにして、更新を習慣にする
- 共有 PC ではログアウト（トークンは `sessionStorage` なのでタブを閉じれば消えます）

### 4-5. 下書きブランチで試す（優先度: 低）

MCP の `GITHUB_BRANCH` を `draft` などにしておくと、公開サイトに出さずに編集結果を貯められます。まとめて確認してから `main` にマージする運用にすれば、書きかけが公開される事故を防げます。
