# 運営ガイド & 改善提案

VOCABUKI EVENT CALENDAR の構成・運用手順と、点検で見つかった課題への対応をまとめたものです。

---

## 1. 今の構成

```
                 ┌──────────────┐
   Claude ──MCP──▶│              │
                 │ events.json  │──fetch──▶ index.html （公開カレンダー）
 admin.html ─────▶│  （唯一の    │
   （ブラウザ）    │   データ源）  │
                 └──────────────┘
                        ▲
                        └── GitHub Contents API 経由でコミット
                            → GitHub Pages が 1〜2 分で再ビルド
```

- **公開ページ**: `index.html`（カレンダー本体。About / Q&A / イベント診断も内包）
- **管理ページ**: `admin.html`（パスワード + GitHub PAT でログインして編集）
- **MCP サーバー**: `mcp/server.mjs`（Claude から直接編集。→ [mcp/README.md](../mcp/README.md)）
- **データ**: `events.json` ただ 1 ファイル（画像は `images/` に別ファイルで置き、パスだけを持つ）

`events.json` のトップレベル構造:

| キー | 内容 |
| --- | --- |
| `events` | イベント配列（スキーマは [mcp/README.md](../mcp/README.md#イベントのフィールド)） |
| `tags` | タグマスタ `{id, label, color}` |
| `people` | 出演者マスタ `{X の ID: {name, x}}` |
| `dayBgMap` | 日付ごとのカレンダー色の上書き |
| `closedDays` | 休業日（カレンダーに「休」と表示） |

## 2. 日常の運用手順

### イベントを追加する

**Claude から（推奨）**
: 「9/5 に◯◯を追加して、DJ は〜」と伝えるだけ。詳細・画像・リンクまで一度に入ります。→ [mcp/README.md](../mcp/README.md)

**admin.html から**
: 週を選んで「＋ イベントを追加」→ カードを開いて編集 → カード内の「💾 保存」→ **画面上部の「💾 保存」**（これを押さないと GitHub に反映されません）

どちらで編集しても同じ `events.json` を触るので、混ぜて使って問題ありません。

### スマホだけで完結させる

**イベントの登録・編集・画像の追加まで、すべてスマホのブラウザだけで完結します。** PC は不要です。

1. スマホのブラウザで `https://vocabuki-io.github.io/eventcalendar/admin.html` を開く
2. ID 欄に GitHub の PAT、パスワード欄に管理パスワードを入れてログイン
   - **「この端末にログインを記憶する」を入れたままにすると、次回からログイン不要**になります（PAT をスマホで打ち直すのは現実的でないため）
   - PAT はパスワード管理アプリに保存しておくと初回入力も楽です
3. 週を選んでイベントカードをタップ → 編集
4. フライヤーは「📎 画像を追加」からカメラロールを選ぶだけ。撮影したままの大きな写真でも自動で縮小されます
5. 画面上部（または下部）の「保存」を押す → 1〜2 分で公開サイトに反映

ホーム画面に追加しておくとアプリのように開けます（iOS: 共有 → ホーム画面に追加）。

> 共有の端末を使うときは「この端末にログインを記憶する」のチェックを外し、終わったら必ずログアウトしてください。ログアウトで端末に保存されたトークンは消えます。

**Claude に頼みたい場合**も、スマホから [claude.ai/code](https://claude.ai/code) を開いてこのリポジトリのセッションを立てれば同じことができます。
`mcp/` のサーバーは PC で動かす前提のものなので、スマホから使うなら claude.ai/code か、上の管理画面を使ってください。

### 反映の確認

保存から 1〜2 分で `https://vocabuki-io.github.io/eventcalendar/` に反映されます。
反映されないときは、GitHub の Actions タブで Pages のビルドが失敗していないか確認してください。

### フライヤー・画像を入れる

`admin.html` のイベントカードで「📎 端末から画像を選ぶ」を押すか、Claude に画像を渡すだけです。
どちらの経路でも、画像は `images/` に**ファイルとして**保存され、`events.json` には `images/20260905-a1b2c3.jpg` のような**パスだけ**が入ります。

- 長辺 1600px を超える画像は自動で縮小し、JPEG に再エンコードします（スマホで撮った 4MB のフライヤーがそのまま入ることはありません）
- 300KB 以下でサイズも収まっている画像はそのまま保存します（小さいロゴなどの透過・文字の鮮明さを保つため）
- アップロード直後は GitHub Pages の公開が追いつかないため、管理画面のプレビューは一時的に手元のデータを表示します

### 出演者の名前

`people` に一度登録すれば、以降は X の ID を書くだけで表示名とアイコンが出ます。
アイコンは `unavatar.io` 経由で X から自動取得しているので、こちらで用意する必要はありません。

## 3. 今回直した不具合

| 箇所 | 症状 | 原因 |
| --- | --- | --- |
| `index.html` 全体 | **曜日が 1 日ずれて表示されていた**（金曜のイベントが「土」など） | 曜日配列が月曜始まりなのに `Date.getDay()`（日曜始まり）で引いていた。6 箇所 |
| `index.html` リスト表示 | 月の並び順が `1月 → 10月 → 11月 → 12月 → 2月` になっていた | 月キーがゼロ埋めされておらず文字列ソートが崩れていた |
| `index.html` UP NEXT / リスト | 追加した順によっては日付順に並ばなかった | 表示前に日付でソートしていなかった |
| `admin.html` 保存処理 | イベントを保存するたびに、本来 `dayBgMap` に入るはずの `dayBg` が**イベント本体に紛れ込んでいた** | 編集用の下書きをそのままイベントにマージしていた |
| `admin.html` 保存処理 | イベントの日付を変更すると、**古い日付のカレンダー色が消えずに残っていた** | 変更前の日付を `dayBgMap` から消していなかった |
| `admin.html` ログイン | PAT を `github_pat_` 込みで貼ると認証に失敗した | トークンに常に `github_pat_` を足していた。今はどちらの形式でも通る |
| `admin.html` 保存処理 | 保存のたびにイベントの並び順が崩れていた | 保存時に日付でソートするようにした |
| 両ファイル | 出演者リストのないイベントを開くと画面が真っ白になった | `djs` / `vjs` が無い場合を考慮していなかった |
| `index.html` UP NEXT | 翌月に予定があるのに「今月はもうイベントがありません」と出た | 実際は「今日以降」を見ているので、月に限定しない文言に変更 |

### スマホで直したところ

実機幅（iPhone SE / 320px）で管理画面を触って、次を直しました。

| 症状 | 対応 |
| --- | --- |
| 入力欄をタップするたび iOS が勝手にズームし、戻らない | タッチ端末では入力欄の文字を 16px にした（iOS が自動ズームする条件を外した） |
| タブが破棄されるたびに PAT を打ち直しになる | 「この端末にログインを記憶する」を追加（既定 ON、ログアウトで消える） |
| iPhone の写真（HEIC）がアップロードできない | `image/*` なら受け付け、変換して JPEG で保存するようにした。変換できない端末では理由を表示する |
| 320px 幅でヘッダーの「保存」「ログアウト」が 2 行に割れる | 折り返さないようにした |
| タグ追加の「＋」「追加」ボタンが画面外にはみ出して押せない | 狭い画面では折り返すようにした |
| タグ削除の「x」が 12×14px しかなく指で押せない | 32px 以上に拡大。「削除」ボタンも 38px 以上にした |
| 出演者の「名前 / X の ID」欄が狭すぎて入力しづらい | 狭い画面では 2 行に折り返すようにした |

## 4. 整理したこと・残っている提案

### 4-1. 使わなくなったファイルを削除（対応済み）

どこからも読まれていなかった次のファイルを削除し、データ源を `events.json` 一本にしました。

`events-2026-Q1.json` / `events-2026-Q2.json` / `people.json` / `meta.json`

内容はすべて `events.json` に入っています。必要になれば Git 履歴から戻せます。

### 4-2. スクレイパーを削除（対応済み）

`.github/workflows/scrape.yml` と `scraper/`、その出力先だった `posts.json` を削除しました。

- 取得結果の `posts.json` を読むコードが存在せず、データが行き止まりになっていた
- X のログインを ID / パスワードで自動化しており、いつ止まってもおかしくない状態だった
- 失敗しても誰も気づかなかった

あわせて `admin.html` の「スクレイパー監視アカウント」欄も削除しました（管理する対象が無くなったため）。
`events.json` の `watchAccounts` キーはデータとしてはそのまま残していますが、もう誰も読みません。消したい場合は言ってください。

告知ポストからイベントを起こしたいときは、**ポストの URL を Claude に渡す**のが今の最短ルートです。読み取って `create_event` まで一気に通ります。

### 4-3. フライヤー画像をファイル方式に統一（対応済み）

`admin.html` は画像を base64 のまま `events.json` に埋め込んでいましたが、`images/` にファイルとして保存する方式に変えました。

| | base64 埋め込み（旧） | ファイル方式（新） |
| --- | --- | --- |
| 誰がダウンロードするか | **全訪問者**。`events.json` はカレンダーを開いた全員が読む | イベント詳細を**開いた人だけ** |
| キャッシュ | 効かない。`events.json` は `?t=` 付きで毎回フル取得している | 効く。画像 URL は変わらないのでブラウザが再利用する |
| 1MB のフライヤー 1 枚の影響 | 全員の通信量が +1.3MB、初回表示が重くなる | `events.json` は +50 バイト程度 |
| 上限 | Contents API の 1MB を超えると **`admin.html` からデータを読めなくなる**（詰む） | 画像 1 枚ずつなので上限に当たらない |
| Git 履歴 | 保存のたびに巨大な差分が積む | 画像は 1 回きり、`events.json` の差分は小さいまま |
| 実装 | 単純（1 コミット） | 少し複雑（画像と JSON で 2 コミット） |

長期的にサイトが重くならないのは明確にファイル方式なので、そちらに寄せました。
アップロード時に長辺 1600px へ縮小・JPEG 再エンコードもかけるので、元が 4MB でも数百 KB に収まります。

> 注意点: カードを開いて画像を選んだ時点でリポジトリに保存されます。その後「キャンセル」しても画像ファイル自体は残ります（`events.json` からは参照されないので表示はされません）。気になる分だけ後で消せば十分です。

### 4-4. 管理ページの鍵はトークンだと理解しておく（運用のみ・未対応）

`admin.html` はブラウザだけで動く静的ページなので、パスワードの照合も JavaScript の中で行われています。ページのソースは誰でも読めるため、**パスワードは「うっかり防止」以上のものにはなりません**。

実際に編集をブロックしているのは **GitHub の PAT** です。したがって:

- PAT は**編集する人ごとに個別に発行**する（誰の操作か履歴で追え、辞めた人の分だけ失効できる）
- 権限は `vocabuki-io/eventcalendar` の **Contents: Read and write だけ**に絞る
- 有効期限は 90 日など短めにして、更新を習慣にする
- 使い終わったら**ログアウト**する。特に共有端末では「この端末にログインを記憶する」のチェックを外す
  - チェックを外した場合はタブを閉じれば消えます。入れた場合は端末に残るので、ログアウトで明示的に消してください

### 4-5. 下書きブランチで試す（未対応・任意）

MCP の `GITHUB_BRANCH` を `draft` などにしておくと、公開サイトに出さずに編集結果を貯められます。まとめて確認してから `main` にマージする運用にすれば、書きかけが公開される事故を防げます。
